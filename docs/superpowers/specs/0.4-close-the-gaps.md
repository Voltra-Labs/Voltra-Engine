# 0.4 — closing the 2D and networking gaps (stages 119–131)

Working file. Delete it once 0.4 is released and every decision below is
under "Decisions" in `docs/ARCHITECTURE.md` (see `docs/superpowers/README.md`).

## Goal

0.3 finished the roadmap. `docs/ARCHITECTURE.md` still lists, decision by
decision, what each subsystem does **not** do yet. 0.4 closes the gaps a
game author hits first — animation blending, the missing joints, a character
that pushes things, a camera that turns, editing many entities at once,
prefab variants, and the three networking gaps a real match needs (interest,
lag compensation, a lobby). 3D is **not** part of 0.4; it gets its own plan
after this release (CLAUDE.md: "3D comes later").

## Non-goals

- Anything 3D, or anything shaped for it (CLAUDE.md rules apply in full).
- A visual graph editor for animators (the RON file stays the source; the
  inspector gets fields, not a node canvas).
- Matchmaking through an online service, NAT punch-through, relays.
- Curve editing of keyframe tangents (eases stay per segment).

## Rules every stage follows

- CLAUDE.md hard rules: 2D only; `winit` only in `voltra-core`, `wgpu` only
  in `voltra-render`, `cpal`/`symphonia` only in `voltra-audio`; versions in
  root `[workspace.dependencies]`; no `unwrap()` outside tests; `log`, never
  `println!`; every public item documented; one concept per file, split
  around ~300 lines, in a move-only commit before growing a file.
- Robust by default: handle empty, despawned, hot reloaded, resized; no
  silent failure (warn once, as the existing code does).
- Before designing, read the stage's existing decision in ARCHITECTURE.md
  (section named below) and the code it points at. Check how Unity / Godot /
  Bevy / Box2D shape the feature; say in the decision why that shape fits.
- Each stage ends with, in the tree:
  1. code + tests (unit tests beside the code, integration tests where the
     crate already has them);
  2. its decision written into ARCHITECTURE.md — extend the existing
     section, and move the closed items out of its **Not yet** list;
  3. a README roadmap row `| 1NN | scope | done |`, after 118;
  4. the user guide updated (the chapter covering the area; any new
     `<!-- ci -->` block must pass `cargo xtask guide`);
  5. the inspector / file format support when the feature has an authored
     side (a component nobody can set in the editor is half a feature);
  6. `cargo fmt --all`, tests of the touched crates, and
     `cargo clippy --workspace --all-targets -- -D warnings` clean.
- Commits: Conventional Commits, scope = crate without `voltra-`, subject
  imperative ≤50 chars. Several commits per stage is fine (move-only split
  first, then feature, then docs). Commit on the current branch; do not push,
  rebase, reset, or amend commits that are not your own.
- Serialized formats stay backwards compatible: every new field has
  `#[serde(default)]`, and every shipped `.ron` in `assets/` and `games/`
  still loads (existing format tests pin this).

## Stages

### 119 — Animator crossfades

ARCHITECTURE: "A state machine chooses the clip; the player plays it" and
"Property animation is clips of eased keys".

- A transition gains `duration` (seconds, default 0 = today's cut). Per
  transition only, no machine-wide default: one place to look.
- During a fade the outgoing clip keeps playing from where it was and the
  incoming one starts; each animated property is written once with
  `lerp(out, in, w)`, `w` going 0→1 linearly over `duration`. Unity's
  `CrossFade`, Godot's `xfade_time`.
- Blending lives in the keyframes layer, not the animator: the player
  learns to sample a clip **without writing** (`AnimationClip::sample` into
  a small per-target buffer), and a blend writes the mix. The animator only
  asks for a fade. This is the general mechanism 120 and 121 reuse — design
  it for N weighted inputs, not two.
- Interpolation per `ValueKind`: floats/vectors/colours lerp, angles lerp
  the short way, discrete values (a `SpriteFrame`, bools) switch at
  `w >= 0.5`. A property only one side animates is taken from that side at
  full weight (no snap to a default).
- A transition fired mid-fade fades from the current mix (freeze the
  outgoing mix as a pose, Unity's "interrupted transition").
- **Exit time counting loops** (from the same Not-yet list): `exit_time`
  above 1.0 on a looping clip means after that many loops.
- Tests: halfway values, angle wrap, discrete switch, interrupt mid-fade,
  duration 0 identical to today, despawned target mid-fade, hot reload
  mid-fade.

### 120 — Blend trees

- A state's motion is either a clip (today) or a blend tree:
  `Blend1D { parameter, children: [(threshold, clip)] }` and
  `Blend2D { x, y, children: [([f32;2], clip)] }` (2D: Unity's "simple
  directional" — choose the triangle/segment around the input, barycentric
  weights; a single child or a point outside the hull clamps sensibly).
- Children share normalized time (sync) so a walk and a run blended keep
  foot phase: the tree's length is the weight-averaged length.
- Uses 119's N-input blend. Crossfades between a tree state and a clip
  state work unchanged.
- Inspector: edit thresholds/positions and pick clips. RON stays readable.
- Tests: weights at, between and outside thresholds; 2D at a child, on an
  edge, in a triangle, outside; sync timing; empty tree warns and runs
  nothing.
- Use it in the `character` example (`crates/voltra-core/examples/
  character.rs`): idle/walk/run by speed.

### 121 — Animator layers and timeline record mode

- **Layers**: a machine has `layers`, each a full state machine with its
  own current state, a `weight` and a `mask` (target paths it may write;
  empty = all) and `blend: Override | Additive`. Layer 0 is today's machine
  (old files load as one layer). Evaluated bottom-up into the same blend
  buffer. Additive only on numeric kinds; discrete properties override.
- **Timeline** (ARCHITECTURE: the keyframes decision, its Not-yet list):
  record mode (with record on, moving/editing a property of an entity under
  the previewing player keys it at the playhead, through the existing
  undo), copy/paste keys, and the clip's own undo history (the Atlas
  Editor's separate history is the precedent). Curve editing stays out.
- Tests: an override layer masked to an arm, an additive layer, weight 0
  is a no-op, an old single-layer file round trips; record mode keying a
  move, undo of a key, paste at the playhead.

### 122 — Joints: wheel, prismatic, mouse; springs; breaking

ARCHITECTURE: "Joints are solved as Box2D v3 solves them, inside every
sub-step". Follow Box2D v3's `b2WheelJoint`, `b2PrismaticJoint`,
`b2MouseJoint` (soft constraints, the same sub-stepping).

- `Wheel` (axis, suspension spring hz/damping, optional motor),
  `Prismatic` (axis, limits, motor, spring), `Mouse` (target point, max
  force, hz/damping — the editor's play-mode drag uses it), revolute
  `spring` (hz/damping toward a rest angle).
- `break_force` / `break_torque` on every joint: past it the joint breaks,
  is removed, and a `JointBroken` event is raised through the physics event
  channel games already read.
- Inspector support for each kind; gizmos for axes and limits.
- Tests in `crates/voltra-physics/tests/joints.rs`: a wheel on a slope
  with suspension settling, a prismatic stopping at limits and driven by a
  motor, a mouse joint pulling a body to a point, a revolute spring
  returning, a joint breaking past its force (event raised, once, and the
  entity despawned mid-step does not panic).

### 123 — Characters push bodies and keep speed on slopes

ARCHITECTURE: "Characters are cast and slid, not simulated" and "One-way
colliders remember what they let through; floors carry by pose".

- Pushing dynamic bodies: on contact the character applies an impulse
  along the contact normal limited by a `push_force` (0 = today), mass
  aware; Godot's `CharacterBody2D` leaves this to the user, Unity's
  `CharacterController.OnControllerColliderHit` does too — we do it in the
  engine because every platformer reimplements it; say so in the decision.
- Constant speed on slopes: an option (`constant_speed_on_slopes`, Godot's
  `floor_constant_speed`) so walking up a slope covers the same horizontal
  ground per second.
- Carry rotation: standing on a turning floor rotates the character's own
  rotation when `carry_rotation` is set (default off, as a capsule upright
  is the common case).
- Tests in `tests/character.rs`: pushing a crate (heavier crate moves
  less), push 0 does not push, constant speed up and down a slope,
  rotation carried and not carried.
- `games/platformer` gets a pushable crate.

### 124 — The camera turns; framing several targets

ARCHITECTURE: "A camera rig is two components…", "Several cameras draw a
frame…".

- The camera's view uses its entity's rotation (the `Transform` already has
  one; today the view ignores it). Culling, picking (`screen → world`),
  pixel-perfect snapping (rotation disables the snap; document it), the
  editor's viewport and parallax must all respect it. Find every place that
  builds the view matrix or the visible rect: a rotated view's visible area
  is the AABB of the rotated rect.
- `CameraShake` gains rotational trauma (`max_angle`), same noise model.
- `CameraFollow2D` gains `targets: Vec<SceneId>` (a single `target` still
  loads), framing their bounds with a margin and optional zoom between
  `min_size`/`max_size`. Cinemachine's Target Group.
- Editor overlay: the dead zone and bounds drawn in the viewport for the
  selected follower.
- Tests: picking through a rotated camera, culling at 45°, shake rotation
  decaying to rest, two targets framed and zoomed, a despawned target
  dropped from the group.

### 125 — Editing many entities at once; numbered duplicates

ARCHITECTURE: "The selection is an ordered set, the last picked its
primary".

- The inspector edits the components **all** selected entities share: a
  field equal across them shows its value, a field that differs shows a
  mixed state (`—`); an edit writes that field (only that field) to every
  entity, as **one** undo step. Unity's multi-object editing. Components
  only some have are listed as such and not editable.
- Duplicates are named `Name (1)`, `Name (2)`… — the next free number among
  siblings (Unity's rule), on duplicate and paste.
- Tests: mixed detection, one undo for N entities, editing one field
  leaving the differing others alone, numbering skipping taken numbers.

### 126 — Prefab variants; nested edits reach without a save

ARCHITECTURE: "An instance follows its file, but for what it overrides"
and "A prefab is edited on its own while the scene waits".

- A variant is a prefab file whose root is an instance of another prefab
  with overrides (Unity's prefab variant). Editing the base reaches the
  variant and its instances except where overridden. Create one from the
  asset browser ("Create Variant").
- Nested instances: saving the inner prefab propagates to outer prefabs'
  instances in the open scene without re-saving the outer file.
- Cycles (a variant of itself, through a chain) are refused before saving.
- Tests: base change reaching a variant and an instance of it, override in
  the variant kept, cycle refused, nested propagation.

### 127 — Interest management

ARCHITECTURE: "The server sends what each client has not acknowledged,
most important first" (it says: "No interest management: every client is
sent every replicated entity").

- Per client, a relevance set: an entity is relevant when within a
  `radius` of any of the client's interest points (by default the entities
  it owns, `NetOwner`), or `Replicated { always_relevant: true }`. A
  uniform spatial grid over replicated entities, rebuilt per tick, answers
  the query (not O(clients × entities)).
- Leaving relevance despawns on the client (reliable, as despawn is);
  entering spawns with full state. Hysteresis (`radius` to enter,
  `radius * 1.1` to leave) so an entity on the edge does not flap.
- Unreal's `NetCullDistanceSquared` + replication graph grid; say why the
  grid and not per-pair distance.
- Editor's network counters show relevant entities per client.
- Tests: entity entering/leaving, hysteresis, always-relevant, owner
  despawned, budget unaffected for relevant ones; a bench in
  `voltra-bench` at 1000 entities × 8 clients.

### 128 — Lag compensation

- The server keeps a ring of the last ~1 s of collider poses of entities
  marked `LagCompensated`. A server-side query (`ray`, `shape`) can be run
  "as the client saw it": at the client's view time = server time −
  (client's interpolation delay + half its RTT), read from the
  interpolation the client reported (`input` already carries ticks; add
  the client's render tick to its input). Clamped to the ring and a
  `max_rewind` (default 200 ms) so a lagging client cannot shoot the past.
- Valve's lag compensation (Source multiplayer networking); Overwatch's
  "favour the shooter" bounded rewind. Record the bound and why.
- `games/arena` uses it for its hit test.
- Tests: a ray that hits a moving target at its past pose but misses its
  present one, a rewind clamped at `max_rewind`, an entity spawned after
  the rewind time not hit, despawned in the window.

### 129 — A lobby and LAN discovery

- A `Lobby` on the server before the match: slots (max players), names,
  ready flags, a host that starts the match when all are ready; typed
  messages over the existing reliable channel. The game decides what
  "start" does (load a scene); the engine owns the protocol and state.
- LAN discovery: the server answers a UDP broadcast probe on a
  configurable port with its name, players and version fingerprint; a
  client lists servers found within a timeout. Native only (no broadcast
  in browsers; say so — the web client joins by address).
- A lobby UI prefab in the template (`cargo xtask new-game`), like the
  options screen: host, find on LAN, join by address, ready, start.
- `games/arena` uses it instead of starting at once.
- Tests: join/leave/ready/start state machine, a full lobby refusing, a
  version mismatch refused at discovery, discovery over loopback.

## Execution

One stage at a time, in order (later stages build on 119's blend, 124's
rotated view, 127's relevance). Per stage: an implementer subagent builds
it to the checklist above and commits; a reviewer subagent, starting cold,
reviews the stage's commits against this spec and CLAUDE.md; findings go
back to the implementer to fix; then the next stage.
