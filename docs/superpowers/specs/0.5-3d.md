# 0.5 — 3D, a parallel subsystem (stages 132–163)

Working file. Delete it once 0.5 is released and every decision below is
under "Decisions" in `docs/ARCHITECTURE.md` (see `docs/superpowers/README.md`).

## Goal

Add 3D to Voltra as a second subsystem beside 2D, in the same engine and
the same `World` — Godot's shape, decided with the user before this spec
(do not reopen it). 2D and 3D share the ECS, assets, scenes and prefabs, the
editor shell and inspector, audio, input, networking and replication, hot
reload and UI. They are separate where the geometry truly differs:
`Transform2D`/`Transform3D`, `Camera2D`/`Camera3D`, 2D/3D physics, the 2D
painter's-order pass / a 3D pass with a depth buffer. One frame can hold
both: by default the 3D world first, 2D world layers over it, the HUD over
everything.

The user ranked, above cost: **(1) comfort for the game developer, (2) code
that is easy to keep developing and improving.** Breaking changes that buy
either are accepted. By 0.5.0 a user can run `cargo xtask new-game my-game
--3d`, drop a glTF character and level into the editor's 3D view, light it
in simple or physical units, give it physics, mouse look and a third-person
camera, animate it, put a 2D HUD and a billboard over it, hear it in 3D,
play it with friends over a LAN or a dedicated server, and ship it to the
web — and `games/courtyard` shows all of it.

The design is the top-level section **"3D: a parallel subsystem (stage
132+)"** in `docs/ARCHITECTURE.md`. Read it before any stage; this spec says
what each stage builds and how it is accepted.

## Non-goals

Each is a later spec of its own, and nothing in 0.5 is shaped for it beyond
what its own stage needs:

- Global illumination of any kind, lightmaps, reflection probes.
- Screen-space effects beyond the existing bloom and grade: SSAO, SSR, TAA,
  depth of field, motion blur.
- Spot and point light shadows; clustered lighting (the per-object list is
  0.5's model — ARCHITECTURE says when clustering is added); histogram
  auto-exposure (0.5's is a log-average).
- Terrain rendering and editing; LOD; occlusion culling; decals.
- 3D particles (`Sprite3D` with tweens covers simple effects).
- Morph targets / blend shapes (the glTF importer warns and ignores them).
- 3D inverse kinematics, ragdoll tooling, vehicles.
- 3D navigation meshes (`voltra-nav` stays a 2D grid).
- A 3D text label, order-independent transparency, pointer input into a UI
  shown on a 3D surface, HRTF and Doppler.
- 2D compound colliders (2D bodies gain non-physics children only).
- A shader graph or a node-based material editor.

**In** 0.5, decided: skeletal skinning and glTF animation (an imported
character that cannot play its walk is not comfort); image-based lighting
from an HDR sky (PBR metals render black without it); one cascaded
directional shadow; physical light units as an opt-in with manual and
automatic exposure (the user's call); fixed-step pose interpolation for
both dimensions (a third-person camera judders without it); mouse look
with cursor grab and pointer lock; a networked 3D sample.

## Rules every stage follows

- **CLAUDE.md hard rules**, as rewritten by stage 132: 2D and 3D are
  parallel subsystems; `winit` only in `voltra-core`, `wgpu` only in
  `voltra-render`, `cpal`/`symphonia` only in `voltra-audio`, `parry3d`
  only in `voltra-physics3d`, `gltf` and `bevy_mikktspace` only in
  `voltra-gltf`; versions in root `[workspace.dependencies]`; no `unwrap()`
  outside tests; `log`, never `println!`; every public item documented;
  one concept per file, split around ~300 lines, **in a move-only commit
  before growing a file** — stages name the splits they already know of;
  any other touched file over the line gets the same.
- **2D is never 3D with z = 0.** No stage widens a 2D type, adds a depth
  buffer to the 2D pass, or gives 2D an axis-named concept. A system both
  dimensions use is generic over both (a trait or a two-variant enum).
  No stage builds scaffolding for a later stage: a type, field or crate
  appears in the stage whose code uses it.
- **Names**: the ARCHITECTURE "Naming" rules. A new 3D component always
  carries `3D`; a twin pair is suffixed on both sides; a registered name is
  spelled only by its type's `NAME` const.
- **WebGL2 is the floor.** Every rendering stage runs on WebGPU *and*
  WebGL2 in the web test harness (`crates/voltra-player/web/test/`), within
  `downlevel_webgl2_defaults` (no storage buffers, no compute, 16 KiB
  uniform blocks, 16 vertex attributes, 255-byte vertex stride, 15
  inter-stage variables, no reversed-Z precision gain). A stage that
  changes what the web build can do updates `docs/WEB.md`.
- **Verify graphics, UI, input and audio APIs** against the vendored
  sources (`~/.cargo/registry/src/index.crates.io-*/`) or Context7 before
  writing GPU, editor UI, input or audio code; new findings go into the
  API tables at the end of ARCHITECTURE.md. New leaf crates (`parry3d`,
  `gltf`, `bevy_mikktspace`) likewise: read their source for the version
  pinned.
- **Robust by default**: handle empty, despawned, hot reloaded, resized,
  missing assets (magenta, warned once), a camera inside geometry, a
  zero-scale or non-finite transform; no silent failure.
- Before designing, read the stage's part of "3D: a parallel subsystem"
  and the existing 2D decision it mirrors (named per stage). Check how
  Godot / Unity / Bevy / Unreal shape the feature; say in the decision why
  that shape fits or does not.
- Each stage ends with, in the tree:
  1. code + tests (unit tests beside the code, integration tests where the
     crate already has them; GPU tests through `voltra-testkit`'s headless
     device, which runs on lavapipe in CI). Every acceptance point is a
     test with a number in it — a tolerance, a pixel, a millisecond — or
     it is not an acceptance point;
  2. its decision written into ARCHITECTURE.md — a Decisions entry of its
     own, with a **Not yet** list — and the "3D: a parallel subsystem"
     section edited to say that part is built;
  3. a README roadmap row `| 1NN | scope | done |`, after 131;
  4. the user guide updated (the chapter named in the stage; any new
     `<!-- ci -->` block must pass `cargo xtask guide`);
  5. inspector and file-format support for every authored component (a
     component nobody can set in the editor is half a feature), and the
     component reachable through the registry, so the MCP server and the
     bridge see it with no code of their own; `docs/MCP.md` updated when a
     tool's answers or a bridge command change;
  6. `cargo fmt --all`, tests of the touched crates, and
     `cargo clippy --workspace --all-targets -- -D warnings` clean.
- **Benchmarks**: a stage that adds a hot path adds a suite to
  `voltra-bench` (named per stage) and `cargo xtask bench --compare` stays
  within the regression check.
- Commits: Conventional Commits, scope = crate without `voltra-`, subject
  imperative ≤50 chars. Several commits per stage is fine (move-only split
  first, then feature, then docs). Commit on the current branch; do not
  push, rebase, reset, or amend commits that are not your own.
- **Formats**: from stage 132 the scene format is version 2. Every new
  field has `#[serde(default)]`; every shipped `.ron` in `assets/` and
  `games/` loads, and `cargo xtask migrate --check` passes over them.
- **Settings** go where ARCHITECTURE "Where settings live" says:
  `default.render.ron` at the asset root, `editor.ron` beside `build.ron`.

## Stages

### 132 — Paired names: `Transform2D` and the format migration

ARCHITECTURE: "Naming", "The migration: format version 2". Mechanical in
bulk, careful at the edges.

- **CLAUDE.md first**, its own commit (`docs: rewrite CLAUDE.md for 2D+3D`).
  Replace "The engine is 2D. 3D comes later" with "2D and 3D are parallel
  subsystems", keeping its spirit:
  - what is shared and what is separate (the ARCHITECTURE table, in short);
  - 2D is never 3D with z = 0: `Vertex2D::position` is `[f32; 2]`, no
    depth buffer in the 2D pass, `sort_order` is 2D-only, 3D has none;
  - do not bend 2D for 3D or 3D for 2D; a shared system is generic over
    both, never a widened 2D type;
  - no speculative scaffolding: a type, field or crate appears in the
    stage whose code uses it;
  - do not name a 2D concept after an axis it is not; the naming rules,
    `NAME` consts for registered names;
  - the 3D world's conventions (Y up, right-handed, −Z forward, metres);
  - the frame order (by priority, 3D before 2D at a tie, overlays
    transparent, the HUD last).
  The crate-ownership hard rules gain `gltf`/`parry3d` only when those
  crates land (143, 148), not now. CONVENTIONS.md gains the naming rule
  (`2D`/`3D` suffix, uppercase `D`, as `PointLight2D` already is).
- **One spelling per registered name**, before the renames: every
  registered type gets a `NAME` const (`Replicated::NAME` is the
  precedent), and every string literal naming a component — about fifty
  across scene, editor and MCP, among them `format/texture_paths.rs`'s
  `"Sprite"`, `prefab/compare.rs`, `prefab/apply.rs`, `prefab/fragment.rs`,
  `prefab/variant.rs`'s `"Transform"`, and
  `voltra-replication/src/client/spawn.rs` — uses it. Its own commit; a
  test greps the sources for a quoted registered name outside its `NAME`.
- **Renames** (code, one move-only commit per crate where it helps
  review): `Transform` → `Transform2D`, scene `Camera` → `Camera2D`,
  `Sprite` → `Sprite2D`, `RigidBody` → `RigidBody2D`, `Collider` →
  `Collider2D`, `WorldTransforms` → `WorldTransforms2D`, and the
  hierarchy's `world_matrix`, `world_transform`, `set_world_transform`,
  `parent_matrix` → `…_2d`; in `voltra-render`, `Camera2D` → `View2D` (no
  alias: it would clash with `voltra_scene::Camera2D` in a glob import),
  `Vertex` → `Vertex2D`, `Mesh` → `Mesh2D`; clip properties
  `Translation`/`Rotation`/`Scale` → `Translation2D`/`Rotation2D`/`Scale2D`
  and `LightColor`/`LightIntensity`/`LightRadius` →
  `PointLight2DColor`/`…Intensity`/`…Radius`, with `#[serde(alias)]` for
  the old names. Registered names follow the types. Doc comments, guide,
  README, templates and examples follow too (`grep -rw Transform` is empty
  of the old meaning when done). `#[deprecated]` aliases for the other
  renamed public items, for 0.5 only, unused in the tree.
- **Format v2** (`format/migrate.rs`): `VERSION = 2`; the loader accepts
  1 and 2 and renames v1 component keys, and component names held as
  values (`PrefabPart::overridden`, prefab variant overrides — find every
  such field; the registry's replication names follow the types), before
  reading. A newer version is refused as today. The migration table is
  data (`&[(from_version, &[(old, new)])]`), so the next rename is one
  line. Prefabs and the staged prefab loader use the same path.
- **Editor**: opening a v1 scene logs once to the Console that the next
  save writes version 2; the scene is not marked dirty. The MCP server
  reads v1 through the same loader.
- **`cargo xtask migrate [folder] [--check]`**: every `.ron` scene, prefab
  and clip under the folder (default: the asset root of each `build.ron`
  in the workspace) read through the engine's loader and written through
  its writer, so the output equals an editor save; `--check` prints what is
  out of date and exits non-zero. Run it over `assets/` and `games/` in a
  commit of its own; CI runs `--check`.
- Tests: a v1 fixture (`crates/voltra-scene/tests/fixtures/v1/`: a scene
  with every renamed component, a prefab instance with overrides naming
  them, a variant, a clip with old property names) loads into the same
  world as its v2 twin; a v2 save of it is byte-identical to the migrated
  file; an unknown component survives migration; a v3 file is refused;
  `migrate --check` fails on the fixture and passes after `migrate`;
  replication of a renamed component round-trips; the literal-name grep.
- Guide: every chapter's names updated; `03-first-game.md` gains a
  "Coming from 0.4" note (the renames, `cargo xtask migrate`);
  `docs/MCP.md`'s component names.

### 133 — `Transform3D`, the hierarchy in two dimensions, `Placement`

ARCHITECTURE: "Conventions of the 3D world", "Animation, prefabs and
replication over both transforms"; the 2D entries "A transform is local,
and the composed one is computed per frame", "The hierarchy is a link on
the child", "An instance follows its file".

- **Move-only splits first**: `hierarchy/link.rs` (544 lines: the rules
  out of the walks), `hierarchy/world_transform.rs` (463: the memoised pass
  out of the single lookups), `prefab/sync.rs` (322).
- `Transform3D { translation: Vec3, rotation: Quat, scale: Vec3 }`
  (default identity, scale one), `matrix() -> Affine3A`, `from_matrix`
  (lossy for shear, as 2D's — say so), `looking_at`, `forward()/right()/up()`,
  `from_euler_degrees` (YXZ). A non-unit or non-finite quaternion read from
  a file is normalised or reset to identity, warned once.
- **Hierarchy**: `Parent` stays shared. `WorldTransforms3D::from_world`
  (memoised, as 2D's) and `world_matrix_3d` and its siblings; `set_parent`
  refuses linking across dimensions (`HierarchyError::MixedDimensions`) —
  a 2D child under a 3D parent has no meaning to compose; an entity with no
  transform passes its children through as 2D does. A file that links
  across dimensions, or an entity carrying both transforms, is warned about
  on load and left alone. The inspector refuses adding the second
  transform. (Physics parenting stays as today until 148.)
- **`Placement`** (`From` either transform) everywhere a root transform is
  named: `prefab::spawn`, `sync` (either root transform untouched),
  `compare` (a root's transform is never an override), `apply` (the
  file's root transform kept), `fragment` (a prefab from a selection is
  zeroed at its root), `variant`, and the replication client's prefab
  spawn.
- **Inspector**: translation and scale fields, rotation as Euler degrees
  with the editor-side hint (typing 180 stays 180); a 3D entity can be
  created from the hierarchy menu (Create ▸ 3D ▸ Empty). No 3D view yet:
  the 2D view does not draw or pick 3D entities, and says so in its
  toolbar when the scene holds some.
- Tests: composition through a chain (rotation then translation order),
  memoised pass equals per-entity walk to 1e-6, cycles terminate,
  mixed-dimension parenting refused and warned, both-transforms file
  warned and kept; a 3D prefab root moved in an instance records no
  override, Apply keeps the file's root transform, a fragment from a 3D
  selection is zeroed at its root, a variant of a 3D prefab; Euler hint
  round trip; a scene with `Transform3D` round-trips byte for byte.
- Guide: new chapter `11-3d.md` begun (coordinates, `Transform3D`,
  parenting rules).

### 134 — 3D values in animation, interpolation and interest

ARCHITECTURE: "Animation, prefabs and replication over both transforms";
the 2D entries "Property animation is clips of eased keys", "A remote
entity is drawn a measured staleness behind", "The owned entity is
predicted…", "Each client is sent what is near what it watches".

- **Keyframes**: `Value::{Vec3, Quat}`, `Property::{Translation3D,
  Rotation3D, Scale3D}`; a rotation mixed by slerp the short way in
  crossfades, blend trees and layers; additive rotation by multiplication.
  (Authoring them in the timeline is 154.)
- **Interpolation**: `Interpolate for Transform3D` (lerp, slerp, lerp;
  equal ends exact); replication registers `Transform3D` interpolated
  (plain postcard until 156).
- **Prediction**: the error metric over either transform (a `distance`
  on `Placement`).
- **Interest**: `server/refresh.rs`'s `Place` reads either transform — a
  2D entity at (x, y), a 3D entity in the same grid at (x, z) with a final
  3D distance test; `set_interest_points` takes `InterestPoint::{D2, D3}`,
  a point seeing only its own dimension; an owned 3D entity adds its
  interest point as a 2D one does. A 3D entity is never "relevant to
  everyone" by having no place.
- Tests: quaternion interpolation the short way and exact at the ends; a
  clip keying `Rotation3D` through a crossfade and an additive layer; a
  3D remote entity interpolated between snapshots; a 3D entity entering
  and leaving relevance by horizontal distance and by height; a 2D point
  does not see a 3D entity; a 3D predicted entity's error metric.
- Guide `08-networking.md`: interest points in 3D (one paragraph; the rest
  is 156).

### 135 — The depth pass: `Camera3D`, meshes, unlit drawing

ARCHITECTURE: "The 3D pass". The 2D entries "Sprites are drawn as
instanced quads", "The batch draws what the camera sees".

- **Render** (`voltra-render/src/render3d/`): `View3D` (view and
  projection; perspective reversed-Z through
  `glam::camera::rh::proj::directx::perspective_infinite_reverse`, or
  finite by swapping near and far; orthographic reversed the same way;
  default `near` 0.1 m), `Vertex3D { position, normal, uv, tangent }`,
  `Mesh3D` (vertex + `u32` index buffers, local bounds), a depth target
  `Depth32Float` cleared to 0 and compared `GreaterEqual`, an instanced
  pipeline drawing a flat colour (materials and lighting are 137). Depth
  target resized with the colour target.
- **Instance layout pinned now** against WebGL2: model as affine `3×vec4`,
  normal matrix `3×vec4`, tint `vec4` (the light-list `Uint32x2` is 139's,
  skin's two attributes 155's) — total 14 of 16 attributes when all land,
  each under the 255-byte stride. A test asserts the count and stride.
- **Scene**: `Camera3D { projection: Perspective { fov_y_degrees, near,
  far: Option } | Orthographic { size, near, far }, priority, active,
  clear }` looking down its entity's −Z; `MeshInstance3D { mesh: AssetPath,
  color }` (137 adds `material`, 140 the shadow flags — each field arrives
  with the code that reads it); `draw3d::from_world` — the world's visible
  instances, culled against the frustum on the CPU (over `voltra-jobs`
  when long), sorted and grouped into instanced draws.
- **Assets**: `Meshes` — built-in primitives `builtin:cube`, `sphere`,
  `plane`, `capsule`, `cylinder` (generated in code with normals, UVs and
  analytic tangents), a magenta cube for a mesh that will not load.
- **Shots**: a full-screen `Camera3D` alone draws through the direct path
  (player and game preview). Several cameras and mixing with 2D are 136.
- Tests (headless GPU): two cubes drawn in either submission order give
  the same picture (depth decides); a cube behind the camera and one past
  a finite far plane are culled; precision — natively, two planes 1 cm
  apart at 500 m resolve; on WebGL2 (web harness), 1 cm apart at 50 m;
  resize keeps depth and colour the same size; zero-scale and despawned
  instances; an orthographic camera; frustum culling unit tests against
  boxes on each plane. Web: a cube scene on WebGPU and WebGL2.
- `docs/WEB.md` and the wgpu API notes: the GL depth remap (ARCHITECTURE
  "The 3D pass").
- Bench: `draw3d` suite — 10 000 instances over 20 meshes, cull + group.
- Guide `11-3d.md`: a first 3D scene by hand (a camera, a cube, a plane).

### 136 — One frame, both worlds

ARCHITECTURE: "One frame, both worlds". The 2D entries "Several cameras
draw a frame", "The frame's post chain is a render graph", "Post-processing
is one graded pass".

- **Order**: `camera::shots` keeps priority as the order (stage 84), with
  3D before 2D at equal priority; texture shots producer before consumer
  (a cycle uses last frame's picture, warned once). `Camera3D` gains
  `viewport` (stage 84's rectangle).
- **Overlay or framing**: a shot overlapped in any part by an earlier
  shot of the other dimension is an overlay and clears transparent; stage
  84's "wholly under a later full-screen camera" pruning applies within a
  dimension only; `clear: Color` forces opaque.
- **3D target**: `Rgba16Float` HDR, MSAA (`default.render.ron` `msaa: 1 |
  4`, default 4, resolved before post), the existing bloom on it, then a
  tonemap (`Camera3D::tonemap: None | Reinhard | Aces | AgX`, default AgX)
  in front of the existing grade, writing the same sRGB picture a 2D shot
  writes; a 3D overlay's alpha passes through.
- **2D overlay**: draws into a transparent target (its light map
  multiplies only its own layer); its grade **unpremultiplies, grades and
  premultiplies again**; the composite blends pictures premultiplied, in
  order; the HUD once.
- **3D into a render texture**: `CameraTarget` on a `Camera3D` (a minimap
  shown by a HUD image), with the same "never draws its own texture" rule.
- Editor: the game preview and play mode show the composite; the 2D view
  still draws 2D only. Project Settings lists `default.render.ron`.
- Tests (headless GPU): a 3D cube with a 2D sprite over it — the sprite's
  pixels over the cube, the cube's elsewhere; a 2D camera's ambient light
  map does not darken the 3D layer under it; a graded 2D overlay's
  alpha-0.5 edge pixel equals the CPU reference (no halo, ±1/255); tonemap
  neutral (`None`) of linear 0.5 reads back 188 as `headless_post.rs` pins;
  MSAA edges have intermediate values, MSAA 1 does not; a 3D picture-in-
  picture at higher priority over a full-screen 2D camera; two full-screen
  2D cameras still draw only the highest; a 3D camera into a render
  texture shown by a HUD image; split screen with a 3D left and 2D right;
  a 3D shot alone keeps the direct path. Web: the mixed scene on both.
- Guide `11-3d.md`: a 3D world with a 2D HUD and a 2D overlay; priorities.

### 137 — Standard surface materials

ARCHITECTURE: "Materials". The 2D entry "A sprite material is a WGSL
fragment function and its uniforms" — mirror it.

- **Format**: `.material.ron` gains `domain: Sprite | Surface` (default
  `Sprite`: every existing file loads unchanged) and a `standard: (...)`
  block (glTF metallic-roughness: base colour and texture, metallic,
  roughness and their texture, normal map and scale, occlusion and
  strength, emissive colour/texture/strength, `alpha: Opaque | Mask(cutoff)
  | Blend`, `double_sided`, `unlit`, `uv_transform`).
- **Shading**: Filament's BRDF (GGX, height-correlated Smith, Schlick),
  Lambert diffuse; normal maps through the tangent; textures sampled from
  the right view (colour sRGB, data raw — the "Data textures" API note).
  `MeshInstance3D` gains `material` (missing: the default white standard).
  A material needs a light to be seen and tested, so this stage brings
  one: `DirectionalLight3D { color, energy }` (one per view here; 139
  makes it a list) and `Environment3D { ambient }` (on the camera's entity,
  or one world entity every camera without one uses — 139 gives it the
  rest). `energy` is stored as ARCHITECTURE "Light units" defines, so 142
  changes no file.
- **Pipelines**: `MaterialBank` keys by (revision, alpha mode,
  double-sided, vertex layout, pass, target format, MSAA); the pass is
  `Main` here, 140 and 146 add `Shadow` and `Id`.
- **Draw order**: opaque and mask front to back by pipeline → material →
  mesh, blend back to front by depth; mask uses alpha-to-coverage under
  MSAA.
- **Editor**: the inspector edits a surface material's file (fields per
  block, texture pickers, colour pickers in linear with sRGB display) with
  a live lit preview sphere; the asset browser shows the same as a
  thumbnail (rendered offscreen, the thumbnail registry's way).
- Tests: a 0.4 sprite material file loads as `Sprite`; GPU — a white unlit
  material reads back white (±1/255); a rough dielectric vs a smooth metal
  under the same light at known pixels match a CPU evaluation of the BRDF
  within 2/255; a normal map tilts the shading; alpha mask cuts, blend
  sorts back to front (two overlapping quads in both submission orders);
  `uv_transform` offsets a texture by a known texel. Web: both backends.
- Guide `11-3d.md`: materials — the standard block, unlit.

### 139 — Lights and the environment

ARCHITECTURE: "Lights, shadows and the environment". The 2D entries on
lights and light layers.

- `PointLight3D`, `SpotLight3D` (colour, `energy`, `range`, spot
  `inner_angle`/`outer_angle`), several `DirectionalLight3D`s, and
  `layers` on every light and on `MeshInstance3D`; Filament's smooth

### 140 — Directional shadows, cascaded

### 157 — 2.5D: `Sprite3D`, 2D on 3D surfaces, the HUD over 3D

ARCHITECTURE: "2.5D bridges".

- **`Sprite3D`**: texture or atlas frame, `color`, `pixel_size` (default
  0.01), `billboard: None | Full | YAxis`, `alpha: Mask(cutoff) | Blend`,
  `shaded`, `double_sided`, `cast_shadows` (masked only); instanced quads
  in the 3D pass, depth-sorted when blended; `SpriteAnimation` and the
  `SpriteColor`/`SpriteFrame` clip properties drive it as they drive a
  `Sprite2D`. Picks by its pixels through the ID pass.
- **2D on a 3D surface**: a surface material may name a
  `.rendertexture.ron`; a `Camera2D` with a `CameraTarget` into it shows a
  2D scene on a mesh (136's producer-before-consumer order). A camera skips
  meshes whose material samples its own target.
- **`UiFollow { target, offset, hide_offscreen }`** places a `UiRect`
  over an entity's projected position, through the camera that draws the
  target's dimension; `Camera3D::world_to_viewport` / `viewport_to_ray`
  public for games.
- Tests: a full billboard faces the camera from any angle (normal within
  0.1°), a Y-axis one stays upright; pixel size gives the expected world
  size; mask casts a cut-out shadow; a 2D scene's red square visible on a
  3D quad in the readback; a camera does not draw its own texture;
  `UiFollow` places a rect over a projected point (±1 px), hides behind
  the camera; the ID pass picks a billboard by its opaque pixels.
- Guide `11-3d.md`: 2D inside 3D.

### 158 — 3D audio

ARCHITECTURE: "3D audio"; the 2D entries on the mixer and
`AudioListener`.

- `voltra_audio::spatial3d`: the same attenuation curve over 3D distance,
  an equal-power pan from the source's direction in the listener's frame
  (right +X, forward −Z), a source behind the listener panned by its side,
  not flipped.
- `AudioSource` / `AudioListener` shared: a source with `Transform3D` is
  heard by the active listener with `Transform3D`; with none it plays
  unpositioned. 2D unchanged.
- **Editor**: source ranges (147's overlay) and the listener icon.
- Tests: full volume at the listener, silent at range; right of the
  listener pans right whatever the listener's world rotation (gain
  difference within 1 %); behind is panned by side; NaN positions silent
  and centred; a 2D source ignores a 3D listener; listener despawned.
- Guide `06-audio.md`: 3D sound.

## Execution

One stage at a time, in order: later stages build on 132's names, 133's
`Placement`, 134's generic values and interest, 135–136's pass and frame,
137–138's materials and passes, 146's ID pass, 148's world, 150–151's
interpolation and input. Per stage: an implementer subagent builds it to
the checklist above and commits; a reviewer subagent, starting cold,
reviews the stage's commits against this spec, ARCHITECTURE.md and
CLAUDE.md; findings go back to the implementer to fix; then the next stage.

- **Who builds what**: stages whose shape is decided and whose work is
  mechanical (132's renames, 159's template) suit a cheaper implementer;
  stages that design under uncertainty (135–136's pass and frame, 140's
  shadows, 142's exposure, 146's ID pass, 148–153's solver and characters,
  155's skinning, 161's networked sample) want the strongest one
  (CLAUDE.md, "Models and delegation").
- **The gate early**: stage 148 may run as soon as 133 has landed, out of
  order, if the user wants the physics answer before the rendering stages;
  its benchmark and its tests need no renderer.
- **Stops**: stage 148's benchmark gate (above); any stage whose robust
  version turns out much larger than this spec says — stop and ask, per
  CLAUDE.md, rather than cut a corner or grow the stage.
- **Sizing**: each stage is one implementer session. A stage that will
  not fit splits at a seam named in it, with a letter suffix (`153a`,
  `153b`), and its README row follows.
