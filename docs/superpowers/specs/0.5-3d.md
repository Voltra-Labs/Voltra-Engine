# 0.5 — 3D, a parallel subsystem (stages 132–154)

Working file. Delete it once 0.5 is released and every decision below is
under "Decisions" in `docs/ARCHITECTURE.md` (see `docs/superpowers/README.md`).

## Goal

Add 3D to Voltra as a second subsystem beside 2D, in the same engine and
the same `World` — Godot's shape, decided with the user before this spec
(do not reopen it). 2D and 3D share the ECS, assets, scenes and prefabs, the
editor shell and inspector, audio, input, networking and replication, hot
reload and UI. They are separate where the geometry truly differs:
`Transform2D`/`Transform3D`, `Camera2D`/`Camera3D`, 2D/3D physics, the 2D
painter's-order pass / a 3D pass with a depth buffer. One frame can hold
both: the 3D world first, 2D world layers over it, the HUD over everything.

The user ranked, above cost: **(1) comfort for the game developer, (2) code
that is easy to keep developing and improving.** Breaking changes that buy
either are accepted. By 0.5.0 a user can run `cargo xtask new-game my-game
--3d`, drop a glTF character and level into the editor's 3D view, light it,
give it physics and a third-person camera, animate it, put a 2D HUD and a
billboard over it, hear it in 3D, play it over the network, and ship it to
the web.

The design is the top-level section **"3D: a parallel subsystem (stage
132+)"** in `docs/ARCHITECTURE.md`. Read it before any stage; this spec says
what each stage builds and how it is accepted.

## Non-goals

Each is a later spec of its own, and nothing in 0.5 is shaped for it beyond
what its own stage needs:

- Global illumination of any kind, lightmaps, reflection probes.
- Screen-space effects beyond the existing bloom and grade: SSAO, SSR, TAA,
  depth of field, motion blur.
- Spot and point light shadows; clustered lighting (the per-object list is
  0.5's model — ARCHITECTURE says when clustering is added).
- Terrain rendering and editing; LOD; occlusion culling; decals.
- 3D particles (`Sprite3D` with tweens covers simple effects).
- Morph targets / blend shapes (the glTF importer warns and ignores them).
- 3D inverse kinematics, ragdoll tooling, vehicles.
- 3D navigation meshes (`voltra-nav` stays a 2D grid).
- A 3D text label, order-independent transparency, pointer input into a UI
  shown on a 3D surface, HRTF and Doppler.
- Physical light units and camera exposure in EV.
- A shader graph or a node-based material editor.

**In** 0.5, decided: skeletal skinning and glTF animation (an imported
character that cannot play its walk is not comfort), image-based lighting
from an HDR sky (PBR metals render black without it), one cascaded
directional shadow.

## Rules every stage follows

- **CLAUDE.md hard rules**, as rewritten by stage 132: 2D and 3D are
  parallel subsystems; `winit` only in `voltra-core`, `wgpu` only in
  `voltra-render`, `cpal`/`symphonia` only in `voltra-audio`, `parry3d`
  only in `voltra-physics3d`, `gltf` (and `mikktspace`) only in
  `voltra-gltf`; versions in root `[workspace.dependencies]`; no `unwrap()`
  outside tests; `log`, never `println!`; every public item documented;
  one concept per file, split around ~300 lines, in a move-only commit
  before growing a file.
- **2D is never 3D with z = 0.** No stage widens a 2D type, adds a depth
  buffer to the 2D pass, or gives 2D an axis-named concept. A system both
  dimensions use is generic over both (a trait or a two-variant enum).
  No stage builds scaffolding for a later stage: a type, field or crate
  appears in the stage whose code uses it.
- **Names**: the ARCHITECTURE "Naming" rules. A new 3D component always
  carries `3D`; a twin pair is suffixed on both sides.
- **WebGL2 is the floor.** Every rendering stage runs on WebGPU *and*
  WebGL2 in the web test harness (`crates/voltra-player/web/test/`), within
  `downlevel_webgl2_defaults` (no storage buffers, no compute, 16 KiB
  uniform blocks, 255-byte vertex stride, 15 inter-stage variables).
- **Verify graphics, UI and audio APIs** against the vendored sources
  (`~/.cargo/registry/src/index.crates.io-*/`) or Context7 before writing
  GPU, editor UI or audio code; new findings go into the API tables at the
  end of ARCHITECTURE.md. New leaf crates (`parry3d`, `gltf`, `mikktspace`)
  likewise: read their source for the version pinned.
- **Robust by default**: handle empty, despawned, hot reloaded, resized,
  missing assets (magenta, warned once), a camera inside geometry, a
  zero-scale or non-finite transform; no silent failure.
- Before designing, read the stage's part of "3D: a parallel subsystem"
  and the existing 2D decision it mirrors (named per stage). Check how
  Godot / Unity / Bevy / Unreal shape the feature; say in the decision why
  that shape fits or does not.
- Each stage ends with, in the tree:
  1. code + tests (unit tests beside the code, integration tests where the
     crate already has them; GPU tests through `voltra-testkit`'s headless
     device, which runs on lavapipe in CI);
  2. its decision written into ARCHITECTURE.md — a Decisions entry of its
     own, with a **Not yet** list — and the "3D: a parallel subsystem"
     section edited to say that part is built;
  3. a README roadmap row `| 1NN | scope | done |`, after 131;
  4. the user guide updated (the chapter named in the stage; any new
     `<!-- ci -->` block must pass `cargo xtask guide`);
  5. inspector and file-format support for every authored component (a
     component nobody can set in the editor is half a feature), and the
     component reachable through the registry, so the MCP server and the
     bridge see it with no code of their own;
  6. `cargo fmt --all`, tests of the touched crates, and
     `cargo clippy --workspace --all-targets -- -D warnings` clean.
- **Benchmarks**: a stage that adds a hot path adds a suite to
  `voltra-bench` (named per stage) and `cargo xtask bench --compare` stays
  within the regression check.
- Commits: Conventional Commits, scope = crate without `voltra-`, subject
  imperative ≤50 chars. Several commits per stage is fine (move-only split
  first, then feature, then docs). Commit on the current branch; do not
  push, rebase, reset, or amend commits that are not your own.
- **Formats**: from stage 132 the scene format is version 2. Every new
  field has `#[serde(default)]`; every shipped `.ron` in `assets/` and
  `games/` loads, and `cargo xtask migrate --check` passes over them.

## Stages

### 132 — Paired names: `Transform2D` and the format migration

ARCHITECTURE: "Naming", "The migration: format version 2". Mechanical in
bulk, careful at the edges.

- **CLAUDE.md first**, its own commit (`docs: rewrite CLAUDE.md for 2D+3D`).
  Replace "The engine is 2D. 3D comes later" with "2D and 3D are parallel
  subsystems", keeping its spirit:
  - what is shared and what is separate (the ARCHITECTURE table, in short);
  - 2D is never 3D with z = 0: `Vertex2D::position` is `[f32; 2]`, no
    depth buffer in the 2D pass, `sort_order` is 2D-only, 3D has none;
  - do not bend 2D for 3D or 3D for 2D; a shared system is generic over
    both, never a widened 2D type;
  - no speculative scaffolding: a type, field or crate appears in the
    stage whose code uses it;
  - do not name a 2D concept after an axis it is not; the naming rules;
  - the 3D world's conventions (Y up, right-handed, −Z forward, metres);
  - the frame order (3D, then 2D, then UI).
  The crate-ownership hard rules gain `parry3d`/`gltf` only when those
  crates land (143, 140), not now. CONVENTIONS.md gains the naming rule
  (`2D`/`3D` suffix, uppercase `D`, as `PointLight2D` already is).
- **Renames** (code, one move-only commit per crate where it helps
  review): `Transform` → `Transform2D`, scene `Camera` → `Camera2D`,
  `Sprite` → `Sprite2D`, `RigidBody` → `RigidBody2D`, `Collider` →
  `Collider2D`, `WorldTransforms` → `WorldTransforms2D`; in
  `voltra-render`, `Camera2D` → `View2D`, `Vertex` → `Vertex2D`, `Mesh` →
  `Mesh2D`; clip properties `Translation`/`Rotation`/`Scale` →
  `Translation2D`/`Rotation2D`/`Scale2D` with `#[serde(alias)]` for the old
  names. Registered names follow the types. Doc comments, guide, README,
  templates and examples follow too (`grep -rw Transform` is empty of the
  old meaning when done). `#[deprecated]` aliases for the renamed public
  types, for 0.5 only, unused in the tree.
- **Format v2** (`format/migrate.rs`): `VERSION = 2`; the loader accepts
  1 and 2 and renames v1 component keys, and component names held as
  values (`PrefabPart::overridden`, prefab variant overrides — find every
  such field; the registry's replication names follow the types), before
  reading. A newer version is refused as today. The migration table is
  data (`&[(from_version, &[(old, new)])]`), so the next rename is one
  line. Prefabs and the staged prefab loader use the same path.
- **Editor**: opening a v1 scene logs once to the Console that the next
  save writes version 2; the scene is not marked dirty. The MCP server
  reads v1 through the same loader.
- **`cargo xtask migrate [folder] [--check]`**: every `.ron` scene, prefab
  and clip under the folder (default: the asset root of each `build.ron`
  in the workspace) read through the engine's loader and written through
  its writer, so the output equals an editor save; `--check` prints what is
  out of date and exits non-zero. Run it over `assets/` and `games/` in a
  commit of its own; CI runs `--check`.
- Tests: a v1 fixture (`crates/voltra-scene/tests/fixtures/v1/`: a scene
  with every renamed component, a prefab instance with overrides naming
  them, a variant, a clip with old property names) loads into the same
  world as its v2 twin; a v2 save of it is byte-identical to the migrated
  file; an unknown component survives migration; a v3 file is refused;
  `migrate --check` fails on the fixture and passes after `migrate`;
  replication of a renamed component round-trips.
- Guide: every chapter's names updated; `03-first-game.md` gains a
  "Coming from 0.4" note (the renames, `cargo xtask migrate`).
- README row: `| 132 | Paired names: Transform2D and friends; scene format 2 and its migration | done |`.

### 133 — `Transform3D` and the hierarchy in two dimensions

ARCHITECTURE: "Conventions of the 3D world", "Animation, prefabs and
replication over both transforms"; the 2D entries "A transform is local,
and the composed one is computed per frame", "The hierarchy is a link on
the child", "An instance follows its file".

- `Transform3D { translation: Vec3, rotation: Quat, scale: Vec3 }`
  (default identity, scale one), `matrix() -> Affine3A`, `from_matrix`
  (lossy for shear, as 2D's — say so), `looking_at`, `forward()/right()/up()`,
  `from_euler_degrees` (YXZ). A non-unit or non-finite quaternion read from
  a file is normalised or reset to identity, warned once.
- **Hierarchy**: `Parent` stays shared. `WorldTransforms3D::from_world`
  (memoised, as 2D's) and `world_matrix_3d`; `set_parent` refuses linking
  across dimensions (`HierarchyError::MixedDimensions`) — a 2D child under
  a 3D parent has no meaning to compose; an entity with no transform passes
  its children through as 2D does. A file that links across dimensions, or
  an entity carrying both transforms, is warned about on load and left
  alone (never an edit made without asking). The inspector refuses adding
  the second transform.
- **Generic from the start**: `prefab::spawn` / `apply` / `sync` take a
  `Placement` (from either transform) and leave either root transform
  untouched; `Interpolate for Transform3D` (lerp, slerp, lerp; equal ends
  exact); keyframes `Value::{Vec3, Quat}` and `Property::{Translation3D,
  Rotation3D, Scale3D}`, a rotation mixed by slerp the short way in
  crossfades, blend trees and layers, additive rotation by multiplication; replication
  registers `Transform3D` interpolated (plain postcard until 148);
  prediction's error metric over either transform (a `distance` on the
  `Placement`).
- **Inspector**: translation and scale fields, rotation as Euler degrees
  with the editor-side hint (typing 180 stays 180); a 3D entity can be
  created from the hierarchy menu (Create ▸ 3D ▸ Empty). No 3D view yet:
  the 2D view does not draw or pick 3D entities, and says so in its
  toolbar when the scene holds some.
- Tests: composition through a chain (rotation then translation order),
  memoised pass equals per-entity walk, cycles terminate, mixed-dimension
  parenting refused and warned, both-transforms file warned and kept;
  prefab placement with a 3D root; quaternion interpolation the short way
  and exact at the ends; a clip keying `Rotation3D` through a crossfade;
  Euler hint round trip; a scene with `Transform3D` round-trips byte for
  byte.
- Guide: new chapter `11-3d.md` begun (coordinates, `Transform3D`,
  parenting rules).

### 134 — The depth pass: `Camera3D`, meshes, unlit drawing

ARCHITECTURE: "The 3D pass". The 2D entries "Sprites are drawn as
instanced quads", "The batch draws what the camera sees".

- **Render** (`voltra-render/src/render3d/`): `View3D` (view and
  projection; perspective reversed-Z through
  `glam::camera::rh::proj::directx::perspective_infinite_reverse`, or with a
  far plane; orthographic with reversed depth), `Vertex3D { position,
  normal, uv, tangent }`, `Mesh3D` (vertex + `u32` index buffers, local
  bounds), a depth target `Depth32Float` cleared to 0 and compared
  `GreaterEqual`, an instanced pipeline drawing a flat colour (materials
  and lighting are 136). Depth target resized with the colour target.
- **Scene**: `Camera3D { projection: Perspective { fov_y_degrees, near,
  far: Option } | Orthographic { size, near, far }, priority, active,
  clear }` looking down its entity's −Z; `MeshInstance3D { mesh: AssetPath,
  color }` (136 adds `material`, 138 the shadow flags — each field arrives
  with the code that reads it); `draw3d::from_world` —
  the world's visible instances, culled against the frustum on the CPU
  (over `voltra-jobs` when long), sorted and grouped into instanced draws.
- **Assets**: `Meshes` — built-in primitives `builtin:cube`, `sphere`,
  `plane`, `capsule`, `cylinder` (generated in code with normals, UVs and
  analytic tangents), a magenta cube for a mesh that will not load.
- **Shots**: a full-screen `Camera3D` alone draws through the direct path
  (player and game preview). Several cameras and mixing with 2D are 135.
- Tests (headless GPU): two cubes drawn in either submission order give
  the same picture (depth decides); a cube behind the camera and one past
  a finite far plane are culled; reversed-Z precision — two planes 1 cm
  apart at 500 m resolve; resize keeps depth and colour the same size;
  zero-scale and despawned instances; an orthographic camera; frustum
  culling unit tests against boxes on each plane. Web: a cube scene on
  WebGPU and WebGL2.
- Bench: `draw3d` suite — 10 000 instances over 20 meshes, cull + group.
- Guide `11-3d.md`: a first 3D scene by hand (a camera, a cube, a plane).

### 135 — One frame, both worlds

ARCHITECTURE: "One frame, both worlds". The 2D entries "Several cameras
draw a frame", "The frame's post chain is a render graph", "Post-processing
is one graded pass".

- **Shots**: `Camera3D` gains `viewport` (stage 84's rectangle) and
  `camera::shots` orders texture cameras first, then per screen
  rectangle 3D shots before 2D shots, then priority; a 2D shot over a 3D
  one clears transparent; a screen camera wholly under a later full-screen
  *opaque* one is still left out, a transparent overlay never hides what
  is under it.
- **3D target**: `Rgba16Float` HDR, MSAA (project setting `msaa: 1 | 4`,
  default 4, resolved before post), the existing bloom on it, then a
  tonemap (`Camera3D::tonemap: None | Reinhard | Aces | AgX`, default AgX)
  in front of the existing grade, writing the same sRGB picture a 2D shot
  writes. The render graph runs the 3D chain; 2D's is unchanged.
- **2D over 3D**: the 2D shot draws into a transparent target (its light
  map multiplies only its own layer; its grade grades only its layer);
  the composite blends pictures premultiplied, in order; the HUD once.
- **3D into a render texture**: `CameraTarget` on a `Camera3D` (a minimap
  shown by a HUD image), with the same "never draws its own texture" rule.
- Editor: the game preview and play mode show the composite; the 2D view
  still draws 2D only.
- Tests (headless GPU): a 3D cube with a 2D sprite over it — the sprite's
  pixels over the cube, the cube's elsewhere; a 2D camera's ambient light
  map does not darken the 3D layer under it; tonemap neutral (`None`) of
  linear 0.5 reads back 188 as `headless_post.rs` pins; MSAA edges have
  intermediate values, MSAA 1 does not; a 3D camera into a render texture
  shown by a HUD image; split screen with a 3D left and 2D right; a 3D
  shot alone keeps the direct path. Web: the mixed scene on both backends.
- Guide `11-3d.md`: a 3D world with a 2D HUD and a 2D overlay.

### 136 — Surface materials: standard PBR, unlit, custom WGSL

ARCHITECTURE: "Materials". The 2D entry "A sprite material is a WGSL
fragment function and its uniforms" — mirror it.

- **Format**: `.material.ron` gains `domain: Sprite | Surface` (default
  `Sprite`: every existing file loads unchanged), a `standard: (...)` block
  (glTF metallic-roughness: base colour and texture, metallic, roughness
  and their texture, normal map and scale, occlusion and strength,
  emissive colour/texture/strength, `alpha: Opaque | Mask(cutoff) |
  Blend`, `double_sided`, `unlit`), optional `shader:` and `uniforms:` and
  up to four `textures:`, and `lighting: Lit | Unlit`.
- **Shading**: Filament's BRDF (GGX, height-correlated Smith, Schlick),
  Lambert diffuse; normal maps through the tangent; textures sampled from
  the right view (colour sRGB, data raw — the "Data textures" API note).
  `MeshInstance3D` gains `material`. A material needs a light to be seen
  and tested, so this stage brings one: `DirectionalLight3D { color,
  energy }` (one per view here; 137 makes it a list) and
  `Environment3D { ambient }` (on the camera's entity, or one world entity
  every camera without one uses — 137 gives it the rest).
- **Custom**: `fn surface(in: SurfaceInput) -> Surface` composed by
  `voltra_render::material` around the fixed vertex stage and lighting,
  `standard_surface(in)` available; checked with naga on load; a broken
  material draws the standard one with its error in the inspector and
  logged once; editing `.wgsl`/`.ron` reloads. `MaterialBank` keys
  pipelines by (revision, alpha mode, double-sided, target format, MSAA).
- **Draw order**: opaque and mask front to back by pipeline → material →
  mesh, blend back to front by depth; mask uses alpha-to-coverage under
  MSAA.
- **Editor**: the inspector edits a surface material's file (fields per
  block, texture pickers, the standard block's colour pickers in linear
  with sRGB display); the asset browser shows a lit sphere thumbnail per
  surface material (rendered offscreen, the thumbnail registry's way).
- Tests: uniform layout and composition (as `material/uniforms.rs`,
  `compose.rs`); a 0.4 sprite material file loads as `Sprite`; GPU — a
  white unlit material reads back white; a rough dielectric vs a smooth
  metal against the same light differ as expected at known pixels; normal
  map tilts the shading; alpha mask cuts, blend sorts back to front (two
  overlapping quads in both submission orders); a broken custom shader
  falls back. Web: the materials scene on both backends.
- Guide `11-3d.md`: materials — the standard block, unlit, a custom
  dissolve.

### 137 — Lights and the environment

ARCHITECTURE: "Lights, shadows and the environment". The 2D entries on
lights and light layers.

- `PointLight3D`, `SpotLight3D` (colour, `energy`, `range`, spot
  `inner_angle`/`outer_angle`), several `DirectionalLight3D`s, and
  `layers` on every light and on `MeshInstance3D`; a smooth
  windowed inverse-square falloff to zero at `range` (Filament's).
- **Forward, per-object lists**: one uniform array per view (up to 4
  directional, 128 point/spot); lights culled against the frustum; each
  instance gets its 8 most important point/spot lights (by estimated
  contribution at its bounds), carried in the instance data. Over the
  caps: the least important are dropped, logged once with the count —
  never silently.
- `Environment3D` gains its background `Color | Gradient { top, horizon,
  bottom }` (`Panorama` is 139), an ambient energy, and distance and
  height fog.
- **Editor**: inspector fields; the 3D view will draw light gizmos (142);
  until then the game preview shows the result.
- Tests: a point light's falloff reaches zero at `range` and is finite at
  0 distance; spot cone edges; 9 point lights on one mesh keep the 8
  brightest; the cap logs once; layers exclude; fog at known depths;
  gradient sky behind geometry only (depth 0 pixels); despawned light
  mid-frame. Web: both backends.
- Bench: `lights3d` — 128 lights × 2 000 instances, list building.
- Guide `11-3d.md`: lighting a scene.

### 138 — Directional shadows, cascaded

ARCHITECTURE: "Lights, shadows and the environment".

- `DirectionalLight3D::shadows: Option<Shadows3D { cascades: 1..=4
  (default 3), max_distance, resolution (default 2048), bias, normal_bias,
  split_blend }>`; one shadowed directional light per view (a second is
  warned once and drawn unshadowed).
- A `Depth32Float` 2D array, one layer per cascade, drawn by a depth-only
  pipeline per cascade over `cast_shadows` instances culled against the
  cascade's box; practical split scheme; cascades fitted to bounding
  spheres and snapped to texels; casters behind the near plane clamped in
  the vertex stage (no `unclipped_depth`); a comparison sampler and PCF in
  the lit shader; `MeshInstance3D` gains `cast_shadows` and
  `receive_shadows` (default true); alpha-mask materials cast cut-out
  shadows.
- Project setting for shadow quality with explicit fields; web defaults
  that fit WebGL2 (2048² max texture is the guaranteed limit).
- **Editor**: a cascade debug view (tint by cascade) in the 3D view's view
  menu when it exists (141); the inspector now.
- Tests (headless GPU): a cube's shadow on a plane where geometry says;
  no acne on a lit plane at grazing angles with default bias; stable
  texels — translating the camera by sub-texel amounts leaves the shadow
  pixels unchanged; a caster behind the camera still shadows; `cast_shadows:
  false` casts none; mask cut-outs. Web: both backends.
- Guide `11-3d.md`: shadows and their knobs.

### 139 — Image-based lighting from an HDR sky

ARCHITECTURE: "Lights, shadows and the environment".

- `Environment3D::background: Panorama { path }` — an equirectangular
  `.hdr` (the workspace `image` gains `hdr`), drawn as the sky, and with
  `ambient: FromSky` it lights: irradiance as 9 SH coefficients computed on
  the CPU, a specular cube prefiltered by GGX importance sampling into its
  mips by fragment passes (no compute), a split-sum BRDF table made once
  per renderer. Done at load and hot reload, under a stable handle; a
  missing or unreadable panorama falls back to the gradient, warned once.
- Size caps (panorama ≤ 8192 × 4096; cube 256² native, 128² on WebGL2 by
  default, a setting).
- Tests: SH of a uniform white panorama is constant white irradiance; the
  BRDF table's known values at its corners; a chrome sphere reflects a
  red/blue split panorama on the right sides; roughness 1 blurs to
  near-irradiance; hot reload swaps the lighting; a too-large file is
  refused with the reason. Web: both backends.
- Guide `11-3d.md`: skies and image-based light.

### 140 — glTF models

ARCHITECTURE: "Models: glTF". The 2D entries "A prefab is a scene file,
and an instance forgets it", "An instance follows its file", "Hot reload
swaps contents under a stable handle".

- **New crate `voltra-gltf`** (only crate naming `gltf` and `mikktspace`;
  versions read from their source when added): `.gltf` and `.glb` into
  engine-neutral `Model` data — primitives (positions, normals, UVs,
  tangents generated with MikkTSpace when absent, indices), materials as
  standard-block values and image references, the node tree with TRS,
  cameras, `KHR_lights_punctual` lights, `KHR_materials_unlit`,
  `KHR_texture_transform` (offset/scale/rotation only). Skins and
  animations are parsed in 146–147; morph targets warned and ignored.
  Untrusted input: URIs only under the asset root or `data:`; accessor
  bounds and index ranges checked; size caps; a failed check refuses the
  file with the reason.
- **Assets**: `Models` (handle per file, sub-assets by label:
  `crate.glb#Mesh0/Primitive0`, `#Material0`), meshes into `Meshes`,
  materials as surface materials, images through `Textures` (PNG and JPEG
  — the workspace `image` gains `jpeg`). Hot reload of the file updates
  every handle.
- **Scene** (`voltra-scene/src/model/`): a model is a prefab whose records
  are generated from the file — node → entity with `Transform3D`, `Name`,
  `MeshInstance3D` per primitive (a child per extra primitive), lights,
  cameras; record ids derived from node path and name so a re-export keeps
  overrides. An instance follows its file on re-import (stage 64 sync).
- **Import settings** `x.glb.import.ron` (scale, material overrides by
  name, `colliders: None | Convex | Mesh` — read by 143; here stored and
  shown), Godot's `.import`.
- **Editor**: the asset browser lists models with a thumbnail; Instantiate
  places one at the origin (drag onto a surface is 141); the inspector
  shows the import settings.
- Tests: hand-written fixtures written by the tests (a triangle `.gltf`
  with a `data:` buffer, a `.glb` with two meshes and a node hierarchy, a
  textured quad, a model with a bad index, a URI escaping the root, an
  oversized accessor) — parse, refuse with reasons, tangents generated, the
  spawned tree's world matrices equal glTF's; re-import keeps an
  instance's override; a renamed node becomes a new record; GPU — the
  textured quad samples its texture in sRGB. Web: a model on both backends.
- Guide: new chapter `12-models.md` (importing, settings, instances).

### 141 — The editor's 3D view: navigation and picking

ARCHITECTURE: "The editor in 3D". The 2D entries "The editor owns the
editor camera", "The selection is an ordered set", "The asset browser is a
dock, and a drop is the placement", "A screenshot is the editor's viewport
draw".

- **The switch**: a 2D/3D toggle in the viewport toolbar; a scene opens in
  3D when it holds a `Transform3D`; the choice remembered per scene in the
  editor's state; `build.ron` `editor.default_view` for new scenes.
- **`ViewportCamera3D`**: fly (right mouse + WASD/QE, wheel = speed,
  Shift), orbit (middle mouse; Alt + left), pan (Shift + middle), dolly
  (wheel), `F` frames the selection's bounds, numpad 1/3/7/5 and a
  clickable axis widget, perspective/orthographic; scoped to the viewport
  as the 2D camera is (hover, `egui_wants_keyboard_input`); clamped
  distances and speeds. The 2D camera is `ViewportCamera2D`.
- **Grid** on the ground plane, fading with distance, its spacing growing
  with height (as 2D's grid doubles).
- **Picking**: an ID pass (the 3D view's draw list into `R32Uint` + depth,
  the pixels around the cursor read back a frame later), giving the entity
  and the world point; icons for lights, cameras and audio sources are
  screen-space handles tested first. Shift/Ctrl add and toggle as in 2D;
  the marquee selects by world bounds inside its sub-frustum.
- **Selection outline** (an ID-mask edge pass) in the selection colour.
- **Drop**: a model, mesh or prefab dropped from the asset browser lands
  on the surface under the cursor (the picked depth), or on the ground
  plane over empty space.
- **Bridge**: `ViewCamera3D` (set position/target/projection) so a
  screenshot of the 3D view can be asked for; `Screenshot` draws the 3D
  view when it is showing.
- Tests: navigation as numbers (orbit keeps the pivot distance, pan moves
  pivot and eye together, frame fits a sphere, clamps); ID pass picks the
  front of two overlapping cubes, and an alpha-masked quad only where it
  is opaque (147 adds the skinned case); a despawn between
  the pass and the readback is ignored; marquee frustum maths; the bridge
  test drives a 3D screenshot under Xvfb as `voltra-editor/tests/bridge.rs`
  does.
- Guide `11-3d.md`: the 3D view.

### 142 — The editor's 3D view: gizmos and authoring

### 143 — 3D physics I: bodies, colliders, the solver

ARCHITECTURE: "Physics: `parry3d` geometry, our dynamics"; the 2D entries
"Physics is in-house…", "A fixed step…", "The broad phase is
sweep-and-prune…", "The solver is TGS Soft…", "Warm starting…",
"`PhysicsMaterial` is a component…", "A collider carries two masks…".

- **Move-only first**: `voltra-physics` → `voltra-physics2d`; game-facing
  types suffixed (`PhysicsWorld2D`, `RayHit2D`, `CollisionEvent2D`,
  `PoseHistory2D`, …); `#[deprecated]` aliases for 0.5. CLAUDE.md's crate
  rules gain `parry3d`.
- **New crate `voltra-physics3d`** over `parry3d` (version read from its
  source; workspace `glam` bumped within 0.33 as its `glamx` needs, so the
  types are the same). Check `cargo xtask dist --web` builds it.
- **Scene**: `RigidBody3D { body_type: Static | Kinematic | Dynamic, mass
  or density, linear/angular damping, gravity_scale, lock axes, velocity,
  angular_velocity, can_sleep }`, `Collider3D { shape: Sphere | Box |
  Capsule | Cylinder | ConvexHull(points) | Mesh(asset) (static only),
  offset }`; shared `PhysicsMaterial`, `CollisionLayers`,
  `Sensor`. A `Mesh` collider on a dynamic body is refused with the reason
  (parry's trimesh is not a volume).
- **Step**: integration (semi-implicit, inverse mass and inertia tensor in
  world space, derived at gather as 2D's is), sweep-and-prune broad phase,
  parry contact manifolds with feature ids, TGS Soft with the same
  `SolverParams` names, warm starting keyed by feature, restitution,
  friction (two tangents), sleeping islands, collision/sensor events
  through the channel games read. Both worlds step in core's fixed tick,
  2D then 3D, each only with bodies. Parenting and physics exclusive, as
  in 2D.
- **glTF** import settings' `colliders` now generate `Collider3D`s.
- **Editor**: inspector; collider wireframes in the 3D view; play mode
  restores 3D bodies as it does 2D ones.
- Tests (`voltra-physics3d/tests/`): a box comes to rest on a plane and
  sleeps; a ten-box stack stays standing 10 s; a sphere rolls down a slope
  at the speed friction allows; restitution bounce heights; a convex hull
  on a mesh floor, across the seam between two triangles, does not snag;
  layers and sensors; events once per begin/end; despawn mid-step.
- Bench: `physics3d` — the ten-stack and a 1000-body pile. **If the stack
  cannot be held or the pile misses the frame budget after tuning, stop
  and report**: the fallback (`rapier3d` behind the same components) is the
  user's call, and ARCHITECTURE records it.
- Guide `04-physics.md`: a 3D section.

### 144 — 3D physics II: queries, CCD, characters

ARCHITECTURE: the 2D entries "Characters are cast and slid, not
simulated", "A fast body is stopped ahead of the solve, and swept after",
"One-way colliders…; floors carry by pose", "A camera rig is two
components".

- **Queries**: `query3d::{ray, shape_cast, overlap}` with the shared
  `QueryFilter` (layers, exclude, sensors), answering `RayHit3D` with
  entity, point, normal, distance.
- **CCD**: speculative contacts plus a swept pass for fast bodies, the
  2D design.
- **`CharacterBody3D`**: a capsule cast and slid (Godot's
  `move_and_slide`): up direction, floor max angle, snap to floor, step
  height (stairs), slide on walls, stop on slopes, constant speed on
  slopes, `push_force` on dynamic bodies, carried by moving floors (pose
  and rotation); `CharacterContact` reports as 2D's.
- **`CameraFollow3D`**: a third-person rig — target, distance, pitch and
  yaw limits, smoothing — and a spring arm shape-cast so the camera never
  passes through walls; a first-person mode (offset, no arm). Driven by
  the game's input (look actions), Cinemachine's third-person follow and
  Godot's `SpringArm3D`.
- Tests: a ray hits the nearest and respects layers; a bullet at
  300 m/s does not tunnel a 5 cm wall; a character walks up a 0.3 m step
  and not a 0.6 m one, stands on a 40° slope and slides off a 60° one,
  keeps speed up a slope, pushes a crate (heavier moves less), rides a
  rotating platform; the camera arm shortens behind a wall and recovers;
  a despawned target.
- Guide `04-physics.md`: characters and queries in 3D.

### 145 — 3D physics III: joints

ARCHITECTURE: the 2D entry "Joints are solved as Box2D v3 solves them".

- **Editor**: inspector per kind; gizmos for axes, anchors and limits.
- Tests (`tests/joints.rs`): a door on a hinge swings to its limit; a

### 146 — 3D animation: clips, the animator and the timeline

### 147 — Skeletal skinning

ARCHITECTURE: the 2D entries "A bone is an entity…" and "A skinned sprite
stores its mesh and weights; the GPU blends its bones".

- **Bones are entities** (as 2D): a glTF skin's joints are its node
  entities; `Skin3D { joints: [paths from the skin root], inverse_binds }`
  on the mesh entity, bound by path so prefab copies bind to their own.
- **GPU**: a skinned `Vertex3D` stream (joint indices `u16x4`, weights
  `unorm16x4`), a joint palette in a uniform block — up to 256 joints as
  3×4 matrices (12 KiB, inside WebGL2's 16 KiB); more is refused with the
  reason. Skinned meshes cast shadows and pick (the ID pass uses the same
  vertex stage). Bounds from the posed joints for culling.
- glTF skins imported; the animator drives the joint entities with 146's
  clips. The 3D view shows bones of the selected skin.
- Tests: a two-joint strip bends as the CPU reference says at known
  vertices; a missing joint path holds its vertices rigidly with the mesh
  (warned once); weights normalised; the posed bounds contain the posed
  vertices; 257 joints refused; the ID pass picks a skinned mesh by its
  posed pixels; an imported skinned character plays its walk headless;
  WebGL2 on the web harness.
- Bench: `skinning3d` — 50 characters × 64 joints, pose + upload.
- Guide `12-models.md`: characters.

### 148 — 3D networking: wire form, interest, lag compensation

ARCHITECTURE: "Animation, prefabs and replication over both transforms";
the 2D entries on snapshots, interpolation, prediction, interest
("Each client is sent what is near what it watches") and lag compensation
("A shot is tested where its shooter saw the target").

- **Wire form**: `ComponentRegistry` learns a per-type wire encoding
  (`replicate_as::<T, Wire>()`); `Transform3D`'s is translation `3×f32`,
  rotation smallest-three (2 + 3×15 bits, canonicalised), scale `f32` when
  uniform else `3×f32`. Error bounds stated and tested.
- **Interest**: 3D entities in the existing grid by (x, z), relevance
  finally tested by 3D distance; `relevance_radius` unchanged.
- **Prediction** already generic (133); a 3D movement in a test.
- **Lag compensation**: `voltra-physics3d::PoseHistory3D` over
  `LagCompensated` `Collider3D`s, `Rewound3D` ray and shape queries at the
  client's view time, clamped by `max_rewind`.

  plays a 3D scene unchanged.
- Tests: a quaternion round trip within the bound at the worst case and
  canonicalised (q and −q encode equal); an unchanged rotation is

  missing its present; `voltra-core/tests/` — a headless server and two

## Execution

One stage at a time, in order: later stages build on 132's names, 133's
generic placement and values, 134–135's pass and frame, 136's materials,
141's ID pass and 143's world. Per stage: an implementer subagent builds it
to the checklist above and commits; a reviewer subagent, starting cold,
reviews the stage's commits against this spec, ARCHITECTURE.md and
CLAUDE.md; findings go back to the implementer to fix; then the next stage.

- **Who builds what**: stages whose shape is decided and whose work is
  mechanical (132's renames, 151's template) suit a cheaper implementer;
  stages that design under uncertainty (134–135's pass and frame, 138's
  shadows, 141's ID pass, 143–145's solver, 147's skinning) want the
  strongest one (CLAUDE.md, "Models and delegation").
- **Stops**: stage 143's benchmark gate (above); any stage whose robust
  version turns out much larger than this spec says — stop and ask, per
  CLAUDE.md, rather than cut a corner or grow the stage.
- **Sizing**: each stage is one implementer session. A stage that will
  not fit splits at a seam named in it (e.g. 136: standard material, then
  custom), with a letter suffix (`136a`, `136b`), and its README row
  follows.
